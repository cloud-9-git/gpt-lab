## 2. 가설 1: BPE vocab을 키우면 한글 tokenization이 좋아진다

### 가설

vocab 3000 BPE tokenizer는 vocab 260 byte tokenizer보다 token 수를 줄이고, 한글 생성에서 byte 깨짐을 줄일 것이다.

### 이유

vocab 260은 특수 토큰 4개와 byte 256개만 있는 상태다.  
한글 한 글자는 UTF-8 byte 여러 개로 구성되기 때문에 byte 단위 생성에서는 잘못된 byte 조합이 나오면 `�`가 생긴다.

BPE vocab을 3000까지 키우면 자주 등장하는 byte 조합이 merge token으로 묶인다.

### 실행 명령

이미 vocab 3000 tokenizer와 cache가 있으면 아래 명령으로 token 수를 확인한다.

```bash
conda run -n gpt-lab python -c "from pathlib import Path; import torch, json; tok=json.loads(Path('data/tokenizer_vocab3000.json').read_text(encoding='utf-8')); print('vocab entries:', len(tok['id_to_token'])); print('merges:', len(tok['merges'])); train=torch.load('data/train_token_ids_vocab3000.pt', map_location='cpu'); val=torch.load('data/val_token_ids_vocab3000.pt', map_location='cpu'); print('train tokens:', train.numel()); print('val tokens:', val.numel())"
```

vocab 260 byte tokenizer와 비교하고 싶으면 아래 명령으로 기존 byte cache도 확인한다.

```bash
conda run -n gpt-lab python -c "from pathlib import Path; import torch, json; tok=json.loads(Path('data/tokenizer.json').read_text(encoding='utf-8')); print('vocab entries:', len(tok['id_to_token'])); print('merges:', len(tok['merges'])); train=torch.load('data/train_token_ids.pt', map_location='cpu'); val=torch.load('data/val_token_ids.pt', map_location='cpu'); print('train tokens:', train.numel()); print('val tokens:', val.numel())"
```

vocab 3000 tokenizer/cache를 새로 만들어야 할 때는 아래 명령을 사용한다.

```bash
MPLCONFIGDIR=.cache/matplotlib python scripts/pretrain_local.py \
  --vocab-size 3000 \
  --context-length 128 \
  --emb-dim 128 \
  --n-heads 4 \
  --n-layers 2 \
  --batch-size 8 \
  --epochs 1 \
  --eval-freq 100 \
  --eval-iter 5 \
  --tokenizer-train-chars 1500000 \
  --train-chars 1500000 \
  --val-chars 120000 \
  --tokenizer-path data/tokenizer_vocab3000.json \
  --train-token-cache data/train_token_ids_vocab3000.pt \
  --val-token-cache data/val_token_ids_vocab3000.pt \
  --results-path outputs/pretrain_vocab3000_check_results.json \
  --loss-plot-path outputs/pretrain_vocab3000_check_loss.png \
  --force-retokenize
```

주의:

- 위 명령은 tokenizer/cache를 새로 만들기 때문에 시간이 걸릴 수 있다.
- token 수만 확인하려면 첫 번째 확인 명령만 실행하면 된다.

### 현재 관찰값

| 항목 | vocab 260 | vocab 3000 |
| --- | ---: | ---: |
| train token 수 | 3,335,336 | 805,112 |
| validation token 수 | 291,753 | 69,868 |

발표 해석:

```text
BPE merge를 통해 같은 NSMC 텍스트를 훨씬 적은 token으로 표현할 수 있었다.
이는 한글 byte 조합과 자주 등장하는 리뷰 표현이 더 큰 token으로 묶였기 때문이다.
```

주의할 점:

```text
token 수 감소 = 무조건 좋은 문장 생성
```

은 아니다. tokenization이 좋아져도 모델이 작고 학습이 부족하면 생성 문장은 여전히 어색할 수 있다.

## 3. 가설 2: 사전 학습한 GPT는 랜덤 GPT보다 감성 분류에 유리하다

이 가설이 발표의 메인 실험이다.

### 가설

NSMC 리뷰 텍스트로 사전 학습한 GPT backbone은 랜덤 초기화 GPT backbone보다 감성 분류 미세 조정에서 더 높은 accuracy와 더 낮은 loss를 보일 것이다.

### 비교할 실험

| 실험 | 설명 | 결과 파일 |
| --- | --- | --- |
| Checkpoint 실험 | `checkpoint_step_3500.pt`를 GPT backbone에 로드 | `outputs/finetune_checkpoint_results.json` |
| Random 실험 | 사전 학습 checkpoint 없이 랜덤 초기화 | `outputs/finetune_random_results.json` |

### 고정 조건

- tokenizer: `data/tokenizer_vocab3000.json`
- vocab_size: 3000
- context_length: 128
- emb_dim: 128
- n_heads: 4
- n_layers: 2
- batch_size: 16
- epochs: 3
- lr: 3e-4
- weight_decay: 0.1

### 실험 2-1. Checkpoint 미세 조정

이미 실행했다면 다시 실행하지 않아도 된다.

처음 실행할 때는 감성 분류 리뷰를 token ID tensor로 바꾸는 cache를 만든다.  
다음 실행부터는 같은 명령어를 그대로 써도 cache를 불러와서 더 빠르게 시작한다.

```bash
python scripts/finetune_local.py \
  --checkpoint-path checkpoint_step_3500.pt \
  --tokenizer-path data/tokenizer_vocab3000.json \
  --vocab-size 3000 \
  --context-length 128 \
  --emb-dim 128 \
  --n-heads 4 \
  --n-layers 2 \
  --batch-size 16 \
  --epochs 3 \
  --lr 3e-4 \
  --weight-decay 0.1 \
  --trainable all \
  --results-path outputs/finetune_checkpoint_results.json \
  --save-model-path checkpoints/finetune_checkpoint.pt
```

현재 확인된 checkpoint 실험 결과:

```text

test accuracy: 약 82.88%
```

## 4. 가설 3: 감성 분류에서는 마지막 pad가 아니라 마지막 실제 token을 봐야 한다

### 가설

감성 분류에서 마지막 위치 `x[:, -1, :]`보다 padding이 아닌 마지막 유효 token hidden state를 쓰는 것이 더 적절하다.

### 이유

리뷰 길이는 서로 다르다. 짧은 리뷰는 `max_length`에 맞추기 위해 뒤쪽에 `<pad>`가 붙는다.

```text
리뷰 token: [<bos>, 재미, 있다, <eos>, <pad>, <pad>, <pad>]
```

이때 `x[:, -1, :]`를 쓰면 실제 리뷰 끝이 아니라 마지막 `<pad>` 위치를 보게 된다.

그래서 현재 코드에서는 마지막 non-pad token을 사용하도록 보완했다.

```text
기존 방식:
마지막 칸을 본다.

개선 방식:
pad가 아닌 마지막 실제 token 위치를 찾아서 본다.
```

발표에서는 이 가설을 “성능 비교 실험”이라기보다 “구현 개선 포인트”로 설명하면 좋다.  
정말 비교 실험으로 만들고 싶다면 `x[:, -1, :]` 방식과 non-pad 방식을 각각 실행해 validation/test accuracy를 비교하면 된다.

### 실행 명령

현재 코드가 non-pad token을 쓰는지 확인한다.

```bash
rg -n "valid_lengths|last_token_idx|pad_id" src/finetune.py
```

예상되는 핵심 코드:

```text
valid_lengths = input_ids.ne(self.pad_id).sum(dim=1).clamp(min=1)
last_token_idx = valid_lengths - 1
pooled = x[batch_idx, last_token_idx]
```

이 개선이 들어간 상태에서 checkpoint 미세 조정을 실행하려면 아래 명령을 사용한다.

```bash
python scripts/finetune_local.py \
  --checkpoint-path checkpoint_step_3500.pt \
  --tokenizer-path data/tokenizer_vocab3000.json \
  --vocab-size 3000 \
  --context-length 128 \
  --emb-dim 128 \
  --n-heads 4 \
  --n-layers 2 \
  --batch-size 16 \
  --epochs 3 \
  --lr 3e-4 \
  --weight-decay 0.1 \
  --trainable all \
  --results-path outputs/finetune_checkpoint_nonpad_results.json \
  --save-model-path checkpoints/finetune_checkpoint_nonpad.pt
```

기존 `x[:, -1, :]` 방식과 진짜 성능 비교까지 하려면 별도 branch나 임시 코드에서 pooling만 되돌린 뒤 같은 명령을 실행해야 한다.  
현재 매뉴얼에서는 코드 안정성을 위해 non-pad 방식만 공식 실행 경로로 둔다.

```text
checkpoint 실험의 test loss < random 실험의 test loss
```

가설 A가 틀리거나 애매한 경우:

```text
사전 학습 모델 규모가 너무 작거나 사전 학습 loss가 아직 높아서 감성 분류에 충분히 도움이 되지 않았을 수 있다.
```

## 9. 한계

발표에서 한계는 솔직하게 말하면 된다.

- 모델 크기가 작다.
- 사전 학습 데이터와 학습 시간이 제한적이다.
- 생성 문장은 아직 문법적으로 어색하다.
- `�` 문자가 완전히 사라지지 않았다.
- 최종 step 3930 checkpoint는 저장하지 못했고, 현재는 `checkpoint_step_3500.pt`를 대표 checkpoint로 사용했다.
- 랜덤 초기화 실험을 아직 실행하지 않았다면, 가설 A는 완전히 검증된 상태가 아니다.

발표용 한 줄:

```text
작은 모델이라 생성 품질은 낮았지만, BPE tokenization과 사전 학습 loss 감소, 감성 분류 정확도를 통해 mini GPT 학습 파이프라인이 동작함을 확인했다.
```
